## Overview

**NyayaSetu** is a Government-of-India standard, compliance-first legal technology platform prototype designed to bridge the legal literacy gap, simplify citizen court procedures, and streamline lawyer-client case collaboration in strict compliance with the **Advocates Act, 1961 (Section 29/33)** and **Bar Council of India Rule 36 (non-solicitation)**.

The interface is engineered according to the official **Guidelines for Indian Government Websites (GIGW)** and **Digital India** UI/UX standards.

---

## Compliance

Before engineering this integration, the official eCourts District Court portal (`https://services.ecourts.gov.in/ecourtindia_v6/`) was inspected:

1. **`robots.txt`**:
   - Request to `https://services.ecourts.gov.in/robots.txt` returns `HTTP 404 Not Found`. There are no automated disallow directives published at root.
2. **Terms of Use & Copyright Policy** (`/ecourtindia_v6/?p=copy_right_policy/index`):
   - Content on the portal may be reproduced free of charge for non-commercial, informational purposes with due credit given to the source: **"eCourts Services (eCommittee, Supreme Court of India)"**.
   - Material must not be used in a derogatory or misleading context.
3. **Disclaimer** (`/ecourtindia_v6/?p=disclaimer/index`):
   - The portal expressly clarifies that data hosted on eCourts is for informational purposes and public facilitation only; it does not constitute certified legal copies for court proceedings.
4. **Human-in-the-Loop CAPTCHA Policy (Strict Non-Bypass)**:
   - NyayaSetu **does NOT** solve, bypass, OCR, or outsource the security captcha.
   - The authentic captcha image generated by eCourts' securimage engine is directly displayed to the human visitor. The visitor reads and manually types the captcha, which is forwarded back to the court portal.
5. **Polite Querying & Rate Limiting**:
   - NyayaSetu strictly enforces **one request at a time per visitor session** with a **minimum 2-second delay** between portal calls.
   - Outbound requests send an identified User-Agent: `Mozilla/5.0 ... (NyayaSetu Citizen Case Search/1.0)`.
   - Inbound client queries are restricted via a **per-IP rate limit** of max 10 searches per minute.
6. **Privacy & Data Minimization**:
   - Judicial records involve real citizens and sensitive disputes. **Zero litigant names, case details, or responses are stored server-side**.
   - The backend maintains only ephemeral in-memory sessions with a **10-minute expiry TTL**.
   - Saved snapshots exist exclusively in the visitor's local browser storage (`localStorage`).

## eCourts CNR Request Flow

NyayaSetu keeps CNR case-detail lookup. The linked [eCourt_Scrapper](https://github.com/abhijeetpandey0008/eCourt_Scrapper) scans cause-list documents for matches; its Streamlit implementation is not a full case-detail lookup. This integration follows the compatible per-session cookie and manual-captcha approach while using the portal's CNR search endpoint.

### Request 1: Portal Session Initialization
- **Method**: `GET`
- **URL**: `https://services.ecourts.gov.in/ecourtindia_v6/`
- **Headers**:
  - `User-Agent`: Desktop browser profile
  - `Accept`: `text/html,application/xhtml+xml,application/xml;q=0.9,*/*;q=0.8`
- **Outcome**: Captures session cookies and any initial `app_token` hidden field. The backend then reads the current AJAX verification header names and token from the portal's `components.js`; these values rotate and must not be hard-coded.

### Request 2: Read Current AJAX Verification Headers
- **Method**: `GET`
- **URL**: the `components.js` script referenced by the home page
- **Headers**: same session `Cookie` and home-page `Referer`
- **Outcome**: Reads the current `delimeter` value and custom verification-header name. Both rotate and are kept only in the in-memory search session.

### Request 3: Create a Captcha Challenge
- **Method**: `POST`
- **URL**: `https://services.ecourts.gov.in/ecourtindia_v6/?p=casestatus/getCaptcha`
- **Headers**:
  - `Accept`: `application/json, text/javascript, */*; q=0.01`
  - `X-Requested-With`: `XMLHttpRequest`
  - `Referer`: `https://services.ecourts.gov.in/ecourtindia_v6/`
  - `Cookie`: the session cookies from Request 1
  - Dynamic verification headers read from `components.js`
- **Body**: `ajax_req=true&app_token=${appToken}`
- **Outcome**: The portal returns the captcha image URL and session `app_token`. The backend fetches that exact image URL with the same cookie jar and returns it to the visitor for manual entry.

### Request 4: Submit CNR & Captcha
- **Method**: `POST`
- **URL**: `https://services.ecourts.gov.in/ecourtindia_v6/?p=cnr_status/searchByCNR/`
- **Headers**:
  - `Content-Type`: `application/x-www-form-urlencoded; charset=UTF-8`
  - `Accept`: `application/json, text/javascript, */*; q=0.01`
  - `X-Requested-With`: `XMLHttpRequest`
  - `delimeter`: current value read from `components.js`
  - The current custom verification header name/value read from `components.js`
  - `Referer`: `https://services.ecourts.gov.in/ecourtindia_v6/`
  - `Cookie`: `SERVICES_SESSID=...; JSESSION=...`
- **Body**: `cino=${cnr}&fcaptcha_code=${captcha}&ajax_req=true&app_token=${appToken}`
- **Response Format**: JSON object:
  ```json
  {
    "status": 0 or 1,
    "errormsg": "...",
    "div_captcha": "...",
    "casetype_list": "<html tables of case details and history>",
    "app_token": "..."
  }
  ```

## Architecture & How It Works

```
[ Visitor Browser (Client) ]
    │
    │  1. POST /api/search/start { cnr }
    ▼
[ NyayaSetu Node Backend / Proxy ] ──── (Polite Delay ≥ 2s) ────► [ services.ecourts.gov.in ]
    │                                                                  │
    │  2. Returns { sessionId, captchaImage (base64) }                 │
    ◄──────────────────────────────────────────────────────────────────┘
    │
    │  3. Visitor views captcha image and types answer
    │  4. POST /api/search/submit { sessionId, captcha }
    ▼
[ NyayaSetu Node Backend ] ───────────── (Exact Headers) ───────► [ services.ecourts.gov.in ]
    │                                                                  │
    │  5. If status === 0 (Invalid Captcha):                           │
    │     - Fetches fresh captcha & returns WRONG_CAPTCHA              │
    │  6. If case not found:                                           │
    │     - Returns explicit CASE_NOT_FOUND error                      │
    │  7. If status === 1:                                             │
    │     - Defensive parser module extracts case & history            │
    │  8. Returns Normalized JSON:                                     │
    │     { cnr, caseType, filingNumber, filingDate,                   │
    │       registrationNumber, registrationDate, status,              │
    │       nextHearingDate, stage, courtAndJudge,                     │
    │       petitioner, respondent, history: [{...}] }                 │
    ◄──────────────────────────────────────────────────────────────────┘
    │
[ Visitor Browser ]
    ├── Renders Case Summary Card + Horizontally Scrollable Hearing Table
    └── Saves Snapshot to localStorage
          ├── Pill badge with status, next hearing, and parties
          └── Shows "Saved <date>, may be out of date" banner with:
                • [ 🔄 Refresh from eCourts ] (starts fresh live query)
                • [ 🌐 Open official page ] (services.ecourts.gov.in)
```

## Defensive Parser & Error Handling

All selectors and normalizations are centralized in `ecourts_parser.js`.
- **Defensive Design**: If any district court table layout omits a field, the parser returns `null` instead of crashing.
- **Explicit Error Codes**:
  - `WRONG_CAPTCHA` (HTTP 400): Returns fresh captcha image so user can immediately retry.
  - `CASE_NOT_FOUND` (HTTP 404): Explains that no case record exists for this CNR.
  - `SESSION_EXPIRED` (HTTP 410): Session exceeded 10-minute TTL.
  - `RATE_LIMITED` (HTTP 429): Per-IP threshold (10 searches/min) exceeded.
  - `PORTAL_UNAVAILABLE` (HTTP 503): Official court portal network error or timeout.
  - **No generic 500 errors are returned**.

### Unit Tests & Anonymized Fixtures
Unit tests run against anonymized HTML fixtures saved in `test_fixtures/`:
- `fixture_success_1.html`: Standard district court case with complete details and 3 hearing history records.

## Assumptions & Known Limits

1. **Layout Fragility**: Whenever the National Judicial Data Grid (NJDG) or eCourts CIS updates its HTML structure, the parser might need adjustments. The saved test fixtures in `test_fixtures/` allow developers to update and verify the parser within seconds.
2. **Geo-Blocking / IP Throttling**: The official eCourts portal may throttle or block server requests originating from foreign datacenter IP ranges (e.g., standard US-East AWS/GCP nodes). If deploying on cloud infrastructure, route requests through an Indian proxy or deploy within an Indian cloud region (e.g., AWS Mumbai `ap-south-1`).
3. **Session Lifetime**: Court portal sessions time out on their server. NyayaSetu enforces a 10-minute TTL to match upstream behavior.
4. **Scope**: Initial phase focuses exclusively on 16-character alphanumeric CNR lookups. Standard case-number search (state, district, court complex, year) can be built as a follow-up phase.

## 🔮 Future Scope & Roadmap

In future releases and production expansions, NyayaSetu will incorporate:
- **Expanded DigiLocker Document Integration**: Direct issuer pulling for court-certified orders, vakalatnama, cause list extracts, and automated tamper-proof evidence verification.
- **Local LLMs for Offline / Air-Gapped Connectivity**: On-device / chamber-hosted models (e.g., Llama 3 / Mistral) enabling confidential statutory legal assistance without external API calls or internet dependency.
- **Enhanced Indic Multilingual Expansion**: Support across all 22 Eighth Schedule Indian languages for voice guidance, statutory drafting, and translation of court proceedings.
- **Zero-Knowledge End-to-End Encryption (E2EE)**: Client-side AES-GCM / hybrid cryptographic vaults for advocate-client chambers, ensuring complete confidentiality under Section 126 of the Indian Evidence Act.
- **Automated Hearing Cause-List Monitoring**: Proactive notifications and automated diary synchronizations across district and high courts.
